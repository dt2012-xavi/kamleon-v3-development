# Auth startup and registration recovery (P1)

## Implemented behavior

- `InitActivity` waits for splash completion, then resolves an explicit startup state. A missing profile and a Firestore read error take different paths. Read errors leave the user on the current screen with a Retry action.
- A valid `/scan?unitId=...&sessionId=...` link is retained in the activity ViewModel's `SavedStateHandle` through login, registration, and activity recreation. The link is removed when `MainActivity` is launched; `MainActivity` removes the intent extras before upload to avoid repeating it on recreation.
- If Firebase Auth has an account but `users/{uid}` is missing, the registration form restarts with that account's email and without password fields. It asks for profile data and consent again. The app never deletes the Firebase Auth account automatically.
- After an Auth account has been created, registration retries reuse it. Firestore profile creation reads from the server and returns an existing profile without overwriting it, so an interrupted verification email request can be retried.
- Login offers a verification email resend for an existing unverified account. A verified account that completes a missing profile proceeds to the app.
- Registration validates the email format locally and lets Firebase Auth decide whether a new account can be created. A collision returns the user to login with sign-in and password recovery options. An incomplete profile can be restarted only for the email on the active Auth session.

## Boundaries

- Firestore security rules and the email Cloud Function must allow the authenticated user to create `users/{uid}` and request verification mail. This implementation does not alter backend configuration.
- The QR upload is consumed once by the receiving activity. A crash after the upload starts but before the backend confirms it still requires server-side idempotency to guarantee exactly-once effects.
- Manual verification with a development Firebase account is required for interrupted registration and deep links; unit tests cannot reproduce the remote Auth/Firestore lifecycle.

## Manual checks

1. Open a `/scan` link while signed out, sign in, and confirm one QR upload.
2. Repeat through new registration and email verification; relaunch the app and confirm the pending link reaches `MainActivity`.
3. Interrupt registration immediately after Auth account creation and before the profile write, then relaunch. Confirm the same account can complete its profile without creating another Auth user.
4. Disconnect the network with an authenticated user and relaunch. Confirm Retry appears, and reconnecting does not send the user to registration.
5. Interrupt after profile creation but before verification email delivery. Sign in and confirm the resend control works.
6. Rotate or recreate the activity during login/onboarding and confirm the restored navigation and pending scan are preserved.
7. Try registering with an existing account email while signed out. Confirm the app does not create or modify that account and returns to login with a recovery explanation.
